# Tarja

Installable web app (PWA) to log everyday expenses (food, groceries, leisure, bills, rent) and, soon, to split them with other people in groups. Each expense gets a category auto-suggested from its text, changeable by the user. Works offline. Free tiers only. `README.md` is the front page.

## Commands

pnpm only. Pin dependencies exactly (`pnpm add -E`).

```bash

pnpm types:check         # tsc -b over app, server and node configs
pnpm types:gen           # wrangler types -> worker-configuration.d.ts (rerun after editing wrangler.jsonc, with .dev.vars moved aside: it adds the secrets)
pnpm lint                # eslint + stylelint (src/**/*.css)
pnpm format / format:check
pnpm storybook           # the design system on :6006, local only (design-system/)
pnpm test                # vitest: `core` (node), `server` (workerd), `front` (jsdom) and `docs` (node: the index above) projects
pnpm test -t "name"      # by test name
pnpm db:migrate          # apply db/migrations to the local D1
pnpm db:migrate:remote   # the same on the production D1: always before deploying a release that needs it
pnpm deploy:prod         # build and deploy to Cloudflare (`pnpm deploy` is pnpm's own command, not this one)
                         # both run on their own from GitHub Actions on a push to main that passes CI and carries a new version; by hand only as a fallback
pnpm db:migrate:prerelease  # the same on the prerelease D1
pnpm deploy:prerelease   # build, migrate and deploy the prerelease Worker; GitHub Actions runs it for any branch but main
```

## Architecture

```
server/          Hono Worker: app.ts (routes, exports AppType), index.ts (entry)
src/             SPA: routes/ (file-based), features/, components/, lib/, assets/styles/
db/              D1 SQL migrations (db/migrations)
core/            pure logic shared by client and server
design-system/   Storybook and the stories (a pnpm workspace package)
```

- `server/` never imports from `src/`. `src/` imports only **types** from `@server/*`. `src/lib` and `src/components` never import from `src/features`.
- `design-system/` imports from `src/` and `core/`; nothing imports from it.
- `core/` imports nothing from React, Hono or Workers.
- Chain the Hono routes on one expression (`new Hono().basePath('/api').get(...)`) so `typeof app` carries the route types to the `hc<AppType>` client in `src/lib/api`. Statements like `app.get(...)` on a separate line lose them.
- `wrangler.jsonc` sends only `/api/*` to the Worker first; every other missing path falls back to `index.html`. A new SPA route needs no config. An unknown `/api/...` answers 404 from the Worker.
- Deploys (ADR-0015, ADR-0040, `docs/specs/repository-structure.md`): GitHub Actions deploys `main` to production once the checks pass and only when its `version` has no GitHub Release yet (the `version` job of `ci.yml` asks; then `release`, migrations first, and `tag`), so only the push of a `chore: release x.y.z` commit deploys and any other push to `main` deploys nothing; any other branch deploys the `prerelease` environment of `wrangler.jsonc` (`prerelease.yml`), a second Worker with its own D1, secrets and Google client. The Worker has no Git connection in Cloudflare: with one, a push would be deployed twice. Never run `wrangler deploy --env prerelease` after a normal build: that output binds the production database. `pnpm deploy:prerelease` rebuilds with `CLOUDFLARE_ENV=prerelease` first, and the `d1` commands read the root config, so they need `--env prerelease` too.
- Versions (`docs/specs/repository-structure.md`): the app's number is the `version` of `package.json` (`MAJOR.MINOR.PATCH`) and it moves only in a commit of its own, `chore: release 1.1.0`, when the owner asks, and that push is what deploys production; the tag and the GitHub Release are made by CI after the deploy, no changelog file, no version pull request. `vite.config.ts` defines `VITE_APP_VERSION` (and, in the prerelease build only, `VITE_APP_COMMIT`, the short commit: production leaves it out so a push that changes no code builds the same files and prompts no update) and `appVersion` (`src/lib/version.ts`) is the one place that reads them; the Settings show it next to the status of `/api/health` in About (`src/features/about`), which the home screen no longer asks.
- `src/routeTree.gen.ts` and `worker-configuration.d.ts` are generated but committed (Prettier and ESLint ignore them).
- Relative imports are `./` inside the same folder; otherwise `@/` (`src/`), `@core/` or `@server/`. Never `../`.
- Offline model (see `docs/specs/offline-sync.md`): expense ids are UUIDs created on the client, writes go through the outbox (IndexedDB, stored under the signed-in user's id like the persisted cache) and `PUT /expenses/:id` is idempotent, deletes are soft (`deletedAt`), conflicts are last-write-wins by `updatedAt`, and sync pages through server changes by the `seq` cursor, never by `updatedAt`. The persisted cache is written at most once a second (each write copies all of it), and at once before an outbox lets go of a confirmed write and as the page is hidden (`createPersister`). Don't add an API that depends on the server assigning ids. Custom categories are the exception to the offline model: managing them needs a connection (`docs/specs/categories.md`), and an expense is never refused for its category.
- Login (`docs/specs/authentication.md`): Better Auth on Hono at `/api/auth/*`, Google only, and neither its tokens nor the address of the picture is ever kept (a database hook nulls the tokens, the mapping of the Google profile leaves the picture out). A write (`POST`, `PUT`, `PATCH`, `DELETE`) of `/api` other than `/api/auth/*` that names an `Origin` other than its own is refused `403 bad-origin` (`server/origin.ts`). `/api/expenses`, `/api/categories`, `/api/income` and `/api/budgets` need a session (`withUser`, `server/user.ts`, which also reads the `user` row, since the cookie cache of a session outlives a deleted account: "the user is gone" is a `401` there and nowhere else); `/api/health` and `/api/auth/*` don't. A user's rows are filed under the Better Auth `user.id`. A Cron Trigger of production (none in the prerelease) runs `dailyCleanup` (`server/cleanup.ts`) once a day: the sessions past their end, the abandoned sign-ins of `verification` and the invitations that ended 30 days ago unaccepted; never an expense, an entry or a push subscription. The secrets (`BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`) are typed in `server/secrets.d.ts`; `.dev.vars.example` lists them. In the app, `AuthGate` (`src/features/auth`) shows the sign-in screen to anybody not signed in, and `UserDataProvider` (`src/lib/offline`) gives the signed-in user their own outbox and cache; a `401` makes the app ask the session again, and only a definite answer signs the user out, never a network error; that answer also deletes the user's local copy, as Sign out does, but only if nothing waits in either outbox. The privacy notice (`PrivacyNotice`, `src/features/auth`; its copy is `privacy.*` in the locales and the contact is `src/lib/contact.ts`) opens from the settings and from the sign-in screen with no request, and says only what the code does: a change to what is stored, logged or sent to a third party changes the notice and its "last updated" date in both locales in the same commit (`docs/specs/settings.md`). Every call to `/api` but `/api/auth/*` and `/api/health` carries the id of the user whose `UserDataProvider` is mounted in `X-Tarja-User` (`bindApiUser`, `src/lib/api/client.ts`), and `withUser` answers `401 other-user` when it is there and is not the session's, so a window left open after the browser changed account never syncs against the other session; an absent header is served.
- **Shared expenses (ADR-0012 to ADR-0014).** A group is a ledger its members share (`shared_groups`, `shared_members`, `shared_entries`, `friend_invitations`, `profile`); a member is a user or a placeholder; an invitation is a link and only for being friends: accepting it makes a new friend of two users, in one batch whose first statement writes the group only while the invitation can be taken (open, not the caller's, the two not friends) and whose second marks it under the same condition, and only the members are written if the mark is this request's, so a lost race writes nothing; a friend exists only from an accepted link, so nobody makes one by typing a name, `PUT /api/groups/:id` makes only groups, and there is no invitation for a dummy, which lives only inside a group, added in its People; a person holds at most `MAX_OPEN_INVITATIONS` open ones; a group holds dummies and friends; a placeholder can be merged into a real member, also when a friend is added in its place, by aliasing (`merged_into`, read through `canonicalMember`, no entry is rewritten). Entries belong to the group, never to a user: never write another user's `expenses` row, and an entry names who made and edited it by their members, never a user id. A member row is never deleted (`left_at`), and leaving or removing needs that member's balance at zero, deleting every balance at zero unless the caller is the only user who hasn't left; after that no write may move what a member who left pays or owes in an entry (`422 member-left`), but deleting it and Undo may. A member who left, or whom the owner removed, can be brought back: adding them as a friend again reopens their row (`reopenMember`, `server/db/members.ts`; a person has one row in a group, so never a second one; the id, name, role and switch stay), only while the group is open, has room and the row isn't open already (`409 already-member`, also for the loser of two requests at once), and it counts toward the open groups and the people of the group, never toward the closed groups or the rows a group ever had. On the device of the person who comes back, `groupsQuery` (`src/lib/api/queries.ts`) sees a group go from closed to open, puts the answer in the cache first and invalidates that group's entries, so they are pulled at once from the device's own cursor; `memberUsers` of the fake server (`src/lib/test/fake-groups.ts`) says which members are one person, and `bringBack` reopens a row as the real server does. A deleted or left group is closed, not erased: read-only (`409 closed` on writes; a member who left reads only up to `left_seq`, so never an entry edited after, and sees only the members who were there then: leaving needs a connection, and the device pushes the group's outbox and pulls it before it asks), a person can archive it, and the per-person switch `show_in_expenses` decides whether it is in that person's expenses. Only the payer of a shared expense has a payment method (credit or restaurant card); for the rest it is paid now. Shared entries use default categories only (the server checks it, unlike for a personal expense). Deleting an account (`DELETE /api/account`, one batch) erases a group where nobody else has an account (a member who left keeps theirs, one who deleted theirs has none), with all its names and entries; every other group keeps its entries under a member with no name, as does any placeholder merged into that member, and one it owned goes to the user who joined first or else closes; a friend closes for the person left, as when a friend is deleted, so an open friend always has a real person on the other side. Every `/api/groups/*` route checks membership and answers a non-member the same `404` as a group that doesn't exist; only making a group with a taken id answers `409 id-taken`. Entries sync through a second outbox with a per-group `seq` (`docs/specs/offline-sync.md`), and the device refuses a write to a group closed for the person before it reaches the outbox; anything that shapes a group (groups, members, invitations, the nickname, the simplified debts switch) needs a connection, and the device refuses it offline before sending anything (`LocalRefusal`, `src/features/groups`). What the server refuses for good is said in words, entry by entry with its own Dismiss (`EntryRefusals`), and lives in memory only. The device offers no Edit of an entry that names somebody who left, and an edit keeps the id, `createdAt` and, while the split isn't touched, the saved cents (a duplicate is a new expense: its cents left are drawn again). Splits are worked out in cents in `core/split.ts` (the shares are what is stored, never a percentage; the cents left of an equal split go to members chosen at random by a seed, a 32-bit integer that the form draws once when it opens with `randomSeed`, `src/lib/random-seed.ts`, and keeps, so the preview is what is saved, while the server only validates the shares stored), balances in `core/balance.ts` and simplified debts in `core/simplify.ts`; the server uses the same code. The debts a group shows (`groupDebts` in `core/group-debts.ts`: pair by pair, or the fewest payments when the owner switches simplified debts on) are worked out once in `GroupView` (`useGroupDebts`) and fed to `GroupBalances` and to Settle up, whose "After this" hint is what the view will show once the settlement is saved; the switch is a view, never a rewrite, so the balance in words, Everyone's balance, the totals of Groups and the server's checks never read it. Your part of a shared expense reaches the lists as derived rows from `core/shared-expense.ts`, never stored as a personal row, so the counting helpers need no change; a settlement counts for nobody. The suggestion of a category from the history reads those rows too (`useYourExpenses`). The JSON export keeps `expenses` the person's own, never a shared row, and gains `groups` (every group the device holds, field by field, no user id or email); the CSV gains the shared rows and a last column, group (`docs/specs/export.md`). A group's own table, to print or download from its settings, is the same for everyone (ADR-0043, `core/group-table.ts`): never the person's side. `useYourExpenses` adds them to the person's own expenses for the screens that add up; `useExpenses` stays the person's own alone, so no shared row reaches the personal outbox or the `expenses` of the JSON. Debts are said in words; their `Amount` adds the cues the person allows (color, sign, and in the balances of a group an arrow, ADR-0028), never `--color-danger`. In a list or a picker the person's own member reads "Ana (You)", Ana being how the group names them (`nameInList` of `useGroupWords`, so equal names stay numbered); in a sentence it is a plain "You". The link of an invitation is `/join/<id>.<signature>` (an HMAC of the id under `BETTER_AUTH_SECRET`, `server/invitation-token.ts`): the signature is never stored in the invitation tables, so a copy of them opens no link (it does travel in the `callbackURL` and the error callback of a sign-in, one record of Better Auth that it keeps for at most 10 minutes, or, if the sign-in is abandoned, until the daily clean-up deletes it), the token never goes in the URL of an API call (`POST /api/invitations/read|accept|decline` take it in the body), every way a link can't be used, whatever the type, shape or length of the token, answers the same `410 gone`, every answer that can carry a link has `Cache-Control: no-store`, a token has one spelling only, and the sign-in comes back only to a path of exactly that shape (`invitationPath`). `/api/profile`, `/api/groups`, `/api/invitations` (the join page reads, accepts and declines one with the link), `/api/push` and the deletion of the account need a session.
- **Notifications (ADR-0025, `docs/specs/notifications.md`).** What is told is decided once, by `noticesFor` (`core/notices.ts`), for the banner and the push alike. Every pull (`syncGroup`, whoever starts it: a screen, the watcher, a push) hands its notices to `onNotices` (`src/lib/offline`). The server pushes only on a `PUT` of an entry that makes the row, after the answer (`waitUntil`), never to its author, and only to an address on a push service's host (any other is `400`), so a stored address can't make the Worker call anywhere else; the address travels in the body, never the URL. `VAPID_PRIVATE_KEY` (a JWK of P-256, which the public key is read from) and `VAPID_SUBJECT` are secrets, one set per environment, typed in `server/secrets.d.ts`. Signing out takes the subscription away.
- Money is an integer in cents plus a currency code, never a float.
- What counts in a month goes through `core/counting.ts` (`countedOn`, `countedCents`, `voucherIncomeOn`, `paidBackCents`), never `amountCents` or `chargeDate` read directly: a restaurant card counts your part (`personalCents`, NULL = the whole amount) on the day it was made (`docs/specs/expense-counting.md`).
- A budget limit is read through `limitFor` (`core/budget.ts`), never from a row of the month directly: the limit a month holds is the row of the latest month up to it, and an amount of 0 means no limit, so removing a limit is writing 0, never deleting the row (`docs/specs/budgets.md`). Percentages are only shown, never typed or stored.
- The expense list (`core/expense-list.ts`, `buildList`) filters, groups and adds up by the day made, not by what counts: its subtotals can differ from the summary and the charts, on purpose. Plans are collapsed before anything is filtered, so Edit and Delete always get every part of a plan (`docs/specs/expense-list.md`).
- Schema in hand-written SQL, no ORM. Migrations reach production before the new code goes live, so each one must work with the code still running: add, never rename or drop. `date` is `YYYY-MM-DD` text; timestamps are epoch milliseconds. An existing expense id owned by another user is rejected, never overwritten.

## Frontend

- TanStack Router (file-based) and TanStack Query. The query client (one per signed-in user) uses `staleTime` 60 s, `retry: false` and `gcTime: Infinity` (the persisted cache is the local copy of the data).
- Styles: plain CSS (no SCSS, no Tailwind), CSS variables from `src/assets/styles/tokens.css`, BEM class names, alphabetical properties, no `!important` (Stylelint enforces it). Combine classes with `clsx`.
- Transitions always use `--duration-*` and `--ease-*`; `prefers-reduced-motion` zeroes the durations in one place. Animate only `transform` and `opacity` where possible.
- Colors are flat (no gradients; the only shadows are `--shadow-popup`, around a list that opens over the page, and the same one under the sticky header, over the phone's bottom bar and over the actions stuck to the foot of a sheet while content scrolls beneath them, ADR-0018, and around the `Banner`) and come only from the semantic `--color-*` tokens in `tokens.css`, defined once with `light-dark()`. Never put a raw color in a component; the one exception is the system color keywords of a `@media (forced-colors: active)` block at the end of a component's CSS, which keep a state drawn by a fill visible (`design-system/DESIGN.md`). Don't add a color without updating the palette table in `design-system/DESIGN.md`.
- **The policy of the pages** (`public/_headers`, "Headers" in `docs/specs/authentication.md`, pinned by `docs/headers.test.ts`): `default-src 'self'`, so a request, an image or a font from another origin, an `eval`, a `<style>` element or a `style="…"` attribute in the markup, and any inline `<script>` but the theme one of `index.html` are refused. Setting a custom property from React (`style={{ '--x': 1 }}`) is fine: it goes through `element.style`. The hash of the inline script is never copied by hand: the build takes it from the HTML it wrote (`csp.config.ts`, the `tarja-content-security-policy` plugin of `vite.config.ts`) into the `%INLINE_SCRIPT_HASHES%` marker. A change to what a page may load changes the policy and its test in the same commit; `pnpm dev` doesn't read `_headers`, so try it on a build (`pnpm build`, then `pnpm preview`). The Worker's `/api` answers carry their own, `default-src 'none'`.
- Browser toolbar color (`theme-color` in `index.html`) mirrors the header surface, `--color-bg-secondary`: keep them in sync.
- **The header hides on scroll** (`docs/specs/header.md`): it is sticky and `useHideOnScroll` (`src/lib`) adds `root__header--hidden`, which only moves it with `transform`. Never take it out of the page or the tab order (no `display`, `visibility`, `inert`, `aria-hidden`): a control in it with `:focus-visible` shows it. The page's `scroll-padding-top` is its height (`--header-height` plus the safe area), the foot has `scroll-padding-bottom` for the bottom bar (`--bottom-nav-height`, which the bar keeps at the height it really has, since a word that wraps at a larger text size grows it) and a toast (`--toast-height`), and the bottom bar doesn't hide. **Scrollbars** (`design-system/DESIGN.md` §5): only under `@media (pointer: fine)` in `base.css`, a stable gutter, thin, no track; never `scrollbar-width: none`, never a scrollbar drawn by script.
- **Screen titles and the focus on a change of screen** (`docs/specs/frontend.md`): every screen's `h1` is a `ScreenTitle` (never a bare `<h1>`; the brand is not a heading), which sets `document.title` to "<heading> – Tarja" and, when its screen has just opened, takes the focus or says its text through the `Announcer` (a polite status that is always in the page; `useAnnounce` is also how something with no place on screen is said). A message that comes and goes (offline, a failed load, a copied link) goes in a `LiveNotice`: a live region that is always in the page with its text changing inside it, since one that arrives already filled is announced inconsistently; a `Notice` that is on screen from its first paint has no role; what changes with every key is read out debounced (`useDebouncedValue`, `SpokenHint`). `useScreenArrivals` (`src/lib`) decides which: a change made from a `nav` (the bar, the header, the tabs of Expenses), from a control marked `data-keeps-focus`, by a swipe or through the history leaves the focus and says the screen; any other moves the focus to the `h1`, with no ring and no scroll. Nothing happens at the first load.
- **Shared components** (`src/components`, described in `design-system/DESIGN.md` "Components"): use `Amount` (money with the cues of which way it goes, fed by `useAmount` of `src/lib/amounts`, which also draws the symbol the person chose), `Notice`, `Toast` (a message that goes away by itself, with an action when there is something to do about it, or a pinned one that stays until it is answered), `Button` and `ButtonLink`, `Field` (the box of a field with its floating label, an `icon` inside and `actions` beside it; `FieldBox` for a control named elsewhere) and `DateRangeFields`, `Select`, `MonthSwitch`, `Card` and `CardList`, `Sheet`, `ChoiceGroup`, `Disclosure`, `Dialog` (a modal box, for what has to be read before going on; its `sheet` variant is the bottom sheet that holds the form of a task and the list filters; a tap outside closes it unless closing would lose what was typed, as the add form, Edit, Duplicate and Settle up would), with the shared expenses `Checkbox` and `BottomNav`, and `Banner` (the notice from the top of a shared expense somebody added, ADR-0025), (the tab bar below 40 rem, with the "+" action in the middle) instead of styling raw elements again. The add form is a sheet opened by the "+" (ADR-0016): the logo and Expenses only lead home, and none of the tabs opens, collapses or changes a form. A row of actions is `Actions`, a quiet hint takes the class `hint` and the size and margin of an `h1`, `h2` or `h3` come from `base.css` (`design-system/DESIGN.md` §4). No new left-border message, no hand-built label and control wrapper, no notched row, collapsible panel or modal copied into the CSS of a feature. An action inside a `Toast` or on a `Sheet` is a `ghost` `Button`, never a box: no L inside an L. A list of options is a `Select`, a native `<select>` that draws the icons of its options where the browser lets it be styled (`appearance: base-select`) and the names alone elsewhere: never a `<select>` styled in a feature, nor a list built by hand. A raw `<button>` is for a control with a look of its own. A new shared component comes with its story in `design-system/stories/components/`; a new token needs none, the Foundations read `tokens.css`.
- Shared components take their copy by props: no `use-intl`, no `virtual:*` import, and only the links (`ButtonLink`, `TabLink` and `BottomNav`) know the router.
- **Mobile-first:** base CSS targets phones (below 40 rem the destinations are a bottom bar, `docs/specs/bottom-navigation.md`; anything anchored to the bottom sits above it); widen with `@media (width >= 40rem)` / `(width >= 64rem)`, never `max-width`. Touch targets are at least `--size-touch` (44 px). Pad edge-anchored layouts with `env(safe-area-inset-*)` (`viewport-fit=cover` is on), use `dvh` instead of `vh`, and let form controls inherit `font: inherit` (16 px) so iOS doesn't zoom on focus.
- **i18n:** `use-intl`. UI copy lives in `src/assets/locales/{en,es}.json`, never hard-coded in components; read it with `useTranslations`. English is the source of the key types. A new key goes into every locale (a test checks key parity). The locale is stored preference, then `navigator.languages`, then `en`, and is not in the URL. The brand name "Tarja" isn't translated.

## Testing

- Vitest with `globals: false`: import `describe`, `it`, `expect` and `vi` from `vitest`.
- Tests sit next to the code they cover (`*.test.ts(x)`), no comments in tests.
- `server` tests run in workerd with a real local D1: `import { env } from 'cloudflare:workers'` and `app.request('/api/...', init, env)`. Routes that need a session get one from `signIn()` (`server/test/session.ts`), which saves a user and a real session cookie in the test database (`signIn(email, name)` makes another user, for the tests of groups).
- `front` tests render the real route tree with `renderApp` (it mounts the real `AppProviders`, signed in as `TEST_USER` through `createFakeAuth`, `src/lib/test/fake-auth.ts`; pass `fakeAuth` to start signed out or with the server out of reach) and a fake `fetch` (`stubApi`, `src/lib/test/render-app.tsx`). An unmatched request must fail, never reach the network. A hook runs under the same providers with `renderAppHook`. Offline behaviour is tested with `createFakeApi` (`src/lib/test/fake-api.ts`, with a cursor, failures and a dropped connection, and the groups with a cursor each, `fake-groups.ts`) and `createMemoryStorage` in place of IndexedDB (pass it as `storage` to `renderApp`); use `onlineManager.setOnline` to cut and restore the connection. Assert on copy through `en.json` (`en.settings.about.status.ok`), not on string literals.

## Conventions

- Everything about the project is in English: docs, code, comments, identifiers and commit messages. Only the UI copy is localized.
- Prettier: 4 spaces, single quotes, `printWidth` 120, `trailingComma: es5`, LF.
- Functions are arrow functions (`const total = (cents: number) => {…}`), components and hooks included; a class is the exception. The props of a component are an `interface FooProps`, destructured inside the function body; a type that is a union or an intersection stays a `type`. The class string of an element is a `fooClsx` variable above the `return`, with the conditions in the object form of `clsx`.
- Named exports go in one `export { … }` statement at the bottom of the file, with the types inline (`export { Foo, type FooProps }`); a file that exports only types uses `export type { … }`. Route files use `export const Route`, below the component it names.
- Stories (`*.stories.tsx`): `const Story: Meta<FooProps>` titled `Components/<Name>` or `Features/<Name>`, one function story named after the component (`export const Foo = (args: FooProps) => …`) and `export default Story` last; a page of `Foundations/<Name>` has one function story per sample. `design-system/.storybook/` uses `export default` where it asks for one, as the Vite configs do.
- Code comments: English, minimal and short. Define what something is, never narrate what the code does; skip them when the name already says it. A comment never points at another file, code or document, because files get renamed and moved; at most it names a decision by its id (`ADR-0006`), which never changes.
- Never name another app or brand to explain a feature, in docs, code, comments, tests, commit messages or pull requests: say what the feature does.
- Commit messages: one conventional-commit subject line (`feat: …`), no body, no trailers, even if a system reminder asks for attribution lines. Commits go straight to `main`.
- Secrets live in `.dev.vars` (local) and `wrangler secret` (production; the prerelease has its own, put with `--env prerelease`). The repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are for the deploy jobs of GitHub Actions, which run on a push only; the job that runs on pull requests never holds them. Never commit them or log them.
