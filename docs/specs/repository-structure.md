# Repository structure

```
server/          Worker (Hono): app.ts (routes and AppType), index.ts (entry)
src/             SPA: routes/ (file-based), features/, components/, lib/, assets/ (styles, locales)
db/              D1 SQL migrations (db/migrations)
core/            pure logic shared by client and server
design-system/   Storybook and the stories of the components (a pnpm workspace package)
public/          static files
```

- `server/` doesn't import from `src/`. `src/` only imports **types** from `@server/*`.
- `design-system/` imports from `src/` and `core/` (as `@/*` and `@core/*`); nothing imports from it. A `packages` entry in `pnpm-workspace.yaml` makes it a workspace member and the root script `storybook` delegates to it. It has its own Vite config and `tsconfig.json` (the `@/*` and `@core/*` paths point up into `src/` and `core/`), without the Cloudflare, router and PWA plugins of the app. `.storybook/` holds the config and the preview. `stories/foundations/` shows the tokens, read from `tokens.css` itself so a new token appears on its own (colors, the category colors, the accents, spacing, type, motion and the icon set), `stories/components/` has one file per shared component, titled `Components/<Name>`, with a single story named after the component whose controls set every prop, and `stories/features/` one file per piece of a feature, titled `Features/<Name>`, with a single story named after the piece whose controls set its props and, when it reads data, what that data is. A piece that reads data from hooks is shown inside `AppData`, which mounts the signed-in person with the fakes of `src/lib/test` (the fake sign-in, memory storage and a fake server behind `fetch` for `/api/*` only), so the story seeds what it needs and no request leaves the page. In those stories the callbacks are `fn()`, which the Actions panel logs; what a component keeps itself, like the open state of a `Disclosure`, is kept in the args (`useArgs`) so the control follows what is clicked, and a router or a provider is a small frame inside the story file. The preview imports `main.css`, wraps every story in the real `LocaleProvider`, `ThemeProvider` and `AccentProvider`, and the toolbar sets the theme, the accent, the language and the viewport (320, 390, 640 and 1024 px). The three choices are written to the same storage the app reads and the providers start again, so a story's own state is lost when one changes. `pnpm storybook` serves it on port 6006, with telemetry off; `storybook-static` is the build output and stays out of git, Prettier and ESLint.
- `core/` imports nothing from React, Hono or Workers (ESLint enforces it). The category classifier, the money helpers, what counts in a month and the list and chart logic live there. Both sides import it as `@core/*`; the server also reaches its own subfolders as `@server/*`, so `../` is never needed.
- `wrangler.jsonc` sets `run_worker_first: ["/api/*"]` and `not_found_handling: "single-page-application"`: any path that isn't `/api/*` or a file falls back to `index.html`, and an unknown `/api/…` answers 404 from the Worker.
- `public/_headers` sets the headers of the static files (the HTML above all) against framing and the referrer; the build copies it to the assets folder and Cloudflare applies it there without serving it ([authentication](authentication.md)). The Worker sets the same ones on its own `/api` answers.
- `worker-configuration.d.ts` (runtime and binding types) is generated with `pnpm types:gen` and committed. Regenerate it after editing `wrangler.jsonc`.
- **Production** is `https://tarja.albz.app`, a custom domain of the Worker that is attached in the Cloudflare dashboard, not in `wrangler.jsonc`; `albz.app` also holds the owner's portfolio. The old address, `tarja.antoniolbz.workers.dev`, is off (`workers_dev` is `false` in `wrangler.jsonc`, since without it each deploy decides). The D1 database `tarja` is bound as `DB` with its `database_id` committed in `wrangler.jsonc` (an id, not a secret). A release goes out on its own: once the checks of a push to `main` pass, the `release` job of GitHub Actions applies the migrations (`pnpm db:migrate:remote`) and deploys (`pnpm deploy:prod`) with the repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` ([ADR-0015](../adr/0015-github-actions-deploys-and-a-prerelease-worker.md), [testing and CI](testing-and-ci.md)). `d1 migrations apply` does nothing when none is pending, and a failed migration stops the deploy. One release runs at a time; a push queued behind it that a newer push overtakes is dropped, and the newer release applies whatever migrations are pending, since every release applies all of them. The Worker has no Git connection in Cloudflare (Settings, Builds): with one, each push would be deployed twice. By hand, as a fallback, it is `pnpm db:migrate:remote`, then `pnpm deploy:prod`. The migrations go first so the new code never meets an old schema, which means each one must work with the code still running: add, never rename or drop. Secrets go up with `wrangler secret put`.
- **Prerelease** is `https://tarja-prerelease.albz.app`, the `prerelease` environment of `wrangler.jsonc`: a second Worker, `tarja-prerelease`, with its own D1 database `tarja-prerelease` bound as `DB` (its own `database_id` under `env.prerelease`, which a test requires to differ from production's), `workers_dev` off, and its address as a custom-domain route in that environment, so only its own deploy touches it (production's domain stays in the dashboard). Any push to a branch other than `main` deploys it, replacing what was there.
    - **The workflow.** `.github/workflows/prerelease.yml` runs `pnpm deploy:prerelease` on a push to any branch but `main`, without waiting for the checks, so that a branch in progress can be tried. It never runs on a pull request, so a run started by a fork cannot hold the secrets, and it uses the same two repository secrets as the release. One deploy runs at a time and the newest push goes next. The Node version is `.nvmrc`, `26`, like CI. The token has to write D1 and Workers, and the custom domain of the prerelease; the first run showed that it does.
    - **The script.** `pnpm deploy:prerelease` builds with `CLOUDFLARE_ENV=prerelease` (the Cloudflare Vite plugin then writes the config of that environment, and the build knows it is the prerelease, which the app shows: [header](header.md)), applies the migrations with `wrangler d1 migrations apply DB --remote --env prerelease` (the `d1` commands read the root `wrangler.jsonc`, so without `--env` they would reach production) and deploys with `wrangler deploy --env prerelease`. `pnpm db:migrate:prerelease` is the middle step alone. Never deploy that environment over a normal build: its output binds the production database.
    - **Secrets.** `wrangler secret put <NAME> --env prerelease`, for its own `BETTER_AUTH_SECRET` and the id and secret of its own Google client ([authentication](authentication.md)). The Worker has to exist, so they go up after its first deploy.
    - **The database is disposable.** Every branch uses the same one; if two branches carry different migrations of the same number, wipe it and let the next deploy migrate it again.
    - **What tells it apart.** The prerelease build names itself: the logo reads `Tarja-pre` ([header](header.md)); the manifest `name` and `short_name` and the page title are `Tarja Pre`, so the two apps sit side by side on a phone; and its icons are the files of `public/prerelease/` (the same set as in `public/`, from a `favicon.svg` whose diagonal line is red instead of blue, made with `pnpm pwa:icons`), which the HTML and the manifest of that build use in place of the usual ones. Production ships that folder too, unused. Its version in the Settings carries the commit it was built from, which production's does not (below).
- **Versions.** The number of the app is the `version` of `package.json`, `MAJOR.MINOR.PATCH` (a test requires that shape), and nothing else holds it. It moves only in a commit of its own, `chore: release 1.1.0`, which the owner asks for when a set of changes deserves a number: minor for a feature, patch for a fix, major for a change that remakes the app. That commit is the marker of the release (`git log --grep "chore: release"`), and the push of it deploys like any other. There is no changelog file: the project commits straight to `main` ([ADR-0015](../adr/0015-github-actions-deploys-and-a-prerelease-worker.md)), and a tool that versions through a pull request of its own (Changesets) would add a second push, and so a second deploy, to every release, plus a GitHub App for the bot's pushes to start the checks. The history is the changelog: its subjects are conventional commits, and the notes of a release are generated from them.
    - **Tag and release.** The job `tag` of `ci.yml` runs after `release` (so only once the deploy has worked) on a push to `main`. It reads the `version`, and if no GitHub Release named `vX.Y.Z` exists it creates one with `gh release create --target <the commit> --generate-notes`, which also creates the tag on that commit. A push that leaves the number as it was finds the release and does nothing, so only the push of a `chore: release` commit makes one. `tag` is the one job with `contents: write` (the workflow's default is `contents: read`), holds no secret of Cloudflare, and a pull request never starts it. The notes list the commits and pull requests since the previous release.
    - **How it reaches the app.** `vite.config.ts` reads `package.json` and defines `import.meta.env.VITE_APP_VERSION` in the build, next to `VITE_PRERELEASE`; `src/lib/version.ts` (`appVersion`) reads it and the Settings show it ([settings](settings.md)). Tests set it with `vi.stubEnv`, and where nothing is set (tests, Storybook) it reads `dev`.
    - **The commit, in the prerelease only.** The prerelease build also defines `VITE_APP_COMMIT`, the first 7 characters of the commit it was built from (`GITHUB_SHA` in GitHub Actions, else `git rev-parse HEAD`; nothing when neither answers), and `appVersion` writes it after the number as semver build metadata, `1.0.0+abc1234`. Every push to a branch is a new prerelease of the same number, so the commit is what tells them apart on a phone. Production leaves it out on purpose: a push that changes no code (the docs, say) then builds the same files, so the service worker finds nothing new and nobody is asked to update.

## Dependencies

- pnpm only, with `save-exact` in `.npmrc`: dependencies are added with `pnpm add -E`. The versions are in `package.json`.
- Install scripts are allowed only for `workerd` and `esbuild`, in `pnpm-workspace.yaml`. pnpm 12 also offers "agent skills" shipped by some packages; the two that offer them, `@tanstack/react-router` and `@tanstack/router-plugin`, are denied: they only feed AI assistants and the build doesn't need them.
- `design-system/` pins the same `react`, `react-dom` and `vite` as the root, so pnpm keeps one copy of React. Storybook 10 (`storybook`, `@storybook/react-vite`, `@storybook/addon-a11y`) needed no install script and offered no agent skills.
- Held back, as of 2026-10-25: TypeScript stays on 6.0, because 7.0 exists but `typescript-eslint` 8.72 requires `<6.1`. ESLint stays on 9, because `eslint-plugin-import` doesn't support ESLint 10.
- Tests use `@cloudflare/vitest-plugin`, which replaces the deprecated `@cloudflare/vitest-pool-workers`. `vite-plugin-pwa` goes with `workbox-build` and `workbox-window` at the same version, and the icons come from `@vite-pwa/assets-generator`.
