# Testing and CI

- Vitest with four projects. `core`: node, for the pure logic. `server`: `@cloudflare/vitest-plugin` runs the tests in `workerd` with a real local D1 (`env` from `cloudflare:workers`). `front`: jsdom and Testing Library, with `stubApi` and `renderApp` in `src/lib/test/render-app.tsx`; `renderApp` mounts the real `AppProviders` (language, theme, sign-in gate and per-user data) over memory storage and a fake sign-in (`createFakeAuth`: signed in as `TEST_USER` unless told otherwise), and tests read their expected copy from `en.json`; `renderAppHook` runs a hook under the same providers. The `server` and `front` projects allow a test 20 s, since the runners of CI are about ten times slower than a laptop; a test that needs hundreds of requests seeds its rows with SQL instead. `docs`: node, checks that the index of `AGENTS.md` lists every ADR and every spec, and that each ADR is numbered and headed as its file name says.
- A request without a handler in a test fails; it never reaches the network.
- `design-system/` goes through `types:check` and `lint` (its CSS too) with the rest. Stories are not tests and there is no Storybook test addon ([ADR-0011](../adr/0011-design-system-in-storybook.md)); CI doesn't build Storybook, so a broken story never stops a release. What only a build catches, a path Vite can't resolve, shows when `pnpm storybook` starts.
- **CI and the hook**: a husky `pre-commit` runs `format:check`, `types:check`, `lint` and `test`. GitHub Actions (`.github/workflows/ci.yml`) runs the same plus `build` on every push to `main`. Once `check` passes, the `release` job applies `db/migrations` to the production D1 (`pnpm db:migrate:remote`) if that folder differs from the last commit whose CI run went green, then runs `pnpm deploy:prod`. The baseline is the last green run, not the push, because a queued run can be dropped and its migrations would go unseen. A failed migration stops the deployment. The job has its own `concurrency` group that never cancels a run in progress. They need two repository secrets: `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` (the "Edit Cloudflare Workers" template plus Account → D1 → Edit). The Worker's own secrets stay in `wrangler secret`.
- **Pull requests.** CI also runs `check` on a pull request to `main`; `release` runs only on a push to `main` (the `if` on the job). The shared expenses branch uses it ([repository structure](repository-structure.md)).
- **Shared expenses.** The maths in `core/` (split, balances, simplify, the personal rows) is tested on its rules rather than on a few examples: shares always add up to the amount, the balances of a group add up to zero, simplified payments settle every balance, and a settlement of more than the debt turns it round. `server` tests make several users with `signIn(email, name)` and check that nobody reads or writes a group they aren't in, that an invitation serves one person once (a direct one leaving no half-made friend when two accept at once), and that leaving or deleting with a balance is refused. A migration that rebuilds a table is run on rows written at the migration before it, in a database of its own (`MIGRATION_DB`, a binding the Vitest config adds), as `0013` is. `front` tests add groups to `createFakeApi` (with a cursor per group, refusals with a code, writes whose answer is lost, and `hold` to keep requests waiting) and cover writing offline, the order and the retries of the outbox of groups, leaving, two accounts on one device, and the form in both tails.
