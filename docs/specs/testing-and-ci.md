# Testing and CI

- Vitest with four projects. `core`: node, for the pure logic. `server`: `@cloudflare/vitest-plugin` runs the tests in `workerd` with a real local D1 (`env` from `cloudflare:workers`). `front`: jsdom and Testing Library, with `stubApi` and `renderApp` in `src/lib/testing/render-app.tsx`; `renderApp` mounts the real `AppProviders` (language, theme, sign-in gate and per-user data) over memory storage and a fake sign-in (`createFakeAuth`: signed in as `TEST_USER` unless told otherwise), and tests read their expected copy from `en.json`; `renderAppHook` runs a hook under the same providers. The `server` and `front` projects allow a test 20 s, since the runners of CI are about ten times slower than a laptop; a test that needs hundreds of requests seeds its rows with SQL instead. `docs`: node, checks the front matter of every ADR and every spec ([the docs](../README.md): the keys, the tags of the list, the ADRs and specs named exist, a spec's `adrs` are the ADRs it links to, its `code` exists), that each ADR is numbered and headed as its file name says, and the deploy configuration (`wrangler.jsonc`, the scripts of `package.json`, the workflows and the icons of the prerelease), and the headers of the static files (`public/_headers`: the same security headers as the Worker's, the policy of the pages and the hash of the inline scripts that the build puts in it, [authentication](authentication.md)), including that the Vite config registers the step that puts the hashes in and that it leaves no marker behind: a release and a prerelease both build with that config, and the prerelease workflow runs no checks of its own.
- **Where a test sits.** Every test is in a `test/` folder inside the folder of the code it covers (`src/lib/i18n/test/locale.test.ts`, `src/features/groups/ledger/test/`, `server/routes/test/`, `core/groups/test/`, `docs/test/`) and imports that code by its alias path (`@/lib/i18n/locale`, `@core/groups/split`, `@server/db/groups`), since `../` is never used in an import. The helpers tests share are in folders named `testing`, which are not test folders: `src/lib/testing` for the `front` tests and the stories (`renderApp`, the fakes, the setup file), `core/testing` for the random inputs of the `core` tests and `server/testing` for the `server` tests (the migrations of the setup file, `signIn`, the groups and push helpers). A test file that grows past a few hundred lines splits by theme into files in the same `test/` folder; the fixtures and helpers its parts share go to a module of the matching `testing` folder named after it (`src/lib/testing/expenses.tsx`, `server/testing/members.ts`, `core/testing/export.ts`), except one that reads a feature, which `src/lib` can't import, and is repeated in each part.
- A request without a handler in a test fails; it never reaches the network.
- **Offline in `front` tests.** `createFakeApi` (`src/lib/testing/fake-api.ts`) is a server with a cursor, failures and a dropped connection, and the groups with a cursor each (`fake-groups.ts`, where `memberUsers` says which members are one person and `bringBack` reopens a member's row as the real server does); `createMemoryStorage` stands in for IndexedDB (passed as `storage` to `renderApp`), `fakeAuth` starts signed out or with the server out of reach, and `onlineManager.setOnline` cuts and restores the connection.
- `design-system/` goes through `types:check` and `lint` (its CSS too) with the rest. Stories are not tests and there is no Storybook test addon ([ADR-0011](../adr/0011-design-system-in-storybook.md)); the job `check` doesn't build Storybook; the job `storybook` builds and deploys it after `release`, and `tag` doesn't wait for it, so a broken story never stops a release ([ADR-0046](../adr/0046-the-storybook-is-published-with-each-release.md)). What only a build catches, a path Vite can't resolve, shows when `pnpm storybook` starts.
- **CI and the hook**: a husky `pre-commit` runs `format:check`, `types:check`, `lint` and `test`. GitHub Actions has two workflows ([repository structure](repository-structure.md), [ADR-0015](../adr/0015-github-actions-deploys-and-a-prerelease-worker.md), [ADR-0040](../adr/0040-production-deploys-only-a-new-version.md)). `.github/workflows/ci.yml` has the job `check`, which runs the same plus `build` on every push to `main` and on a pull request to `main`, and holds no secret; the job `version`, which needs `check`, runs on a push only, holds no secret and answers `new` when no GitHub Release exists for the `version` of `package.json`; and the job `release`, which needs `version` and runs only when the version is new, applies the migrations and deploys to production, so a push whose checks fail, or that carries a version already released, is not deployed. The job `storybook` needs `release`, runs under the same condition and deploys the Storybook (`pnpm deploy:storybook`), with the same two secrets after the install. The job `tag` needs `release`, runs under the same condition and creates the GitHub Release `vX.Y.Z` (and its tag) when none exists for the `version` of `package.json`; it is the only job with `contents: write`. It cannot be tried before a push to `main`: its first real run is the first push of the project after this change. `.github/workflows/prerelease.yml` deploys the prerelease on a push to any other branch, which runs no CI.
- **The prerelease.** A test reads `wrangler.jsonc` and fails if `env.prerelease` binds the same D1 database as the top level, or lacks its own, since a deploy of that environment over a normal build would otherwise reach production data. It fails too when the scripts stop pairing `--env prerelease` with a prerelease build (`CLOUDFLARE_ENV=prerelease`), the migrations included, or when `public/prerelease/` stops holding the same icon files as `public/` (in another color). The same test file fails when the `version` of `package.json` is not `MAJOR.MINOR.PATCH` ([versions](repository-structure.md)). The workflows are read as text: the prerelease workflow runs on a push to a branch other than `main` and never on a pull request, one deploy at a time, and deploys with `pnpm deploy:prerelease` without ever naming a production script; the `version` job needs `check`, runs on a push only, asks `gh release view` and holds no secret; the `release` job needs `version`, runs on a push only and only for a new version, migrates before it deploys and never runs two at once; the `tag` job runs after `release`, on a push of a new version, holds the only `contents: write` and no secret, and checks for the release before it creates one; the `storybook` job runs after `release`, on a push of a new version, holds the secrets only after the install, and `tag` doesn't need it; `design-system/wrangler.jsonc` serves `storybook-static` on `tarja-storybook.albz.app` with no binding; and no secret appears in `check`, which a pull request can start.
- **Shared expenses.** The maths in `core/` (split, balances, simplify, the personal rows) is tested on its rules rather than on a few examples: shares always add up to the amount, the cents left of an equal split land on every member over many seeds, the balances of a group add up to zero, simplified payments settle every balance, and a settlement of more than the debt turns it round. `server` tests make several users with `signIn(email, name)` and check that nobody reads or writes a group they aren't in, that an invitation serves one person once (leaving no half-made friend when two accept at once), and that leaving or deleting with a balance is refused. `front` tests add groups to `createFakeApi` (with a cursor per group, refusals with a code, writes whose answer is lost, and `hold` to keep requests waiting) and cover writing offline, the order and the retries of the outbox of groups, leaving, two accounts on one device, and the form in both tails, with `randomSeed` (`src/lib/random/random-seed.ts`) mocked to choose who gets the cents left.
- **Lighthouse, by hand.** Not part of CI and never a dependency: the CLI through `pnpm dlx`, or its Node module installed outside the repository when the dark theme is wanted. Run on a build on localhost, never production: `pnpm build`, `pnpm preview` against the local D1, behind a small proxy that compresses with brotli as Cloudflare does (the preview sends nothing compressed, so every number would come out too slow) and adds the cookie of a test user to every request (`--extra-headers` is not enough: once the app has a cookie of its own the browser stops sending the injected one). The test users are made straight in the local D1 with a session, the cookie signed with the `BETTER_AUTH_SECRET` of `.dev.vars` as Better Auth signs it, never through Google and never with the owner's session, and are filled through the API of the preview as the app would (expenses, income, budgets, custom categories, a friend from an accepted link, a group, a pinned tab, a nickname so its prompt doesn't cover the screen, and an open invitation of somebody else's for the join page). Lighthouse overrides an emulated `prefers-color-scheme`, and a browser flag doesn't take in headless mode, so the dark theme is measured by storing the app's own choice (`tarja:theme` = `dark`) on the origin first and keeping storage between runs; check one final screenshot of each theme, as a dark one can look like the veil of a dialog over the light theme. The pass of 2026-11-22 covered every screen (Expenses and a pinned tab, Groups, a group and its settings, `/groups/new`, Summary, Charts, Budgets, Settings and its three pages, the join page, and the sign-in screen without the cookie), light and dark, phone and desktop: accessibility and best practices at 100 everywhere once the day groups of the list became `h2` under the `h1`; performance 99 to 100 on desktop and 81 to 89 on a throttled phone, which is the download of a first visit ([frontend](frontend.md)).
