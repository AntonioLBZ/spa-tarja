# Data model

Hand-written SQL migrations in `db/migrations`, applied with `wrangler d1 migrations`; no ORM. The schema is small and `wrangler` already is the migration tool. Queries are typed next to the code that runs them and tested in `workerd` against a real D1.

- Amount as an integer in cents plus a currency code, never a `float`. There is a single currency for now (`EUR`, `DEFAULT_CURRENCY` in `core/`); the code is stored on each row so adding more later needs no migration.
- `id` is a UUID created on the client ([offline sync](offline-sync.md)) and is the primary key. `PUT /expenses/:id` creates the row or updates it, but only when it belongs to the caller: an existing id owned by another user is rejected, never overwritten.
- Columns: `user_id`, `category_id`, `text`, `amount_cents`, `currency`, `date`, `created_at`, `updated_at`, `deleted_at` and `seq`.
- `date` is the day the user picked, as `YYYY-MM-DD` text (no time zone to get wrong). `created_at`, `updated_at` and `deleted_at` are epoch milliseconds.
- `updated_at` is the client clock and only decides conflicts ([offline sync](offline-sync.md)). It can't be the sync cursor: an edit made offline last week arrives with an old `updated_at`, and a device whose cursor is already past it would never pull it. The cursor is `seq`, a per-user counter the server bumps on every write (`MAX(seq) + 1` inside the upsert, which D1 serializes).
- Indexes: `(user_id, date)` for listing and `(user_id, seq)` for the sync by delta. Soft deletes travel as rows with `deleted_at` set, so the delta query sees them.
- `categories` holds the custom categories ([categories](categories.md)), in migration `0002`; migration `0004` adds their `color` and `icon`.
- Rows belong to the signed-in user ([authentication](authentication.md)), resolved in a single place in the server.

## Shared expenses

All additive: nothing in the tables above changes ([ADR-0004](../adr/0004-data-conventions.md)). The rules are in [groups](groups.md), [shared expenses](shared-expenses.md) and [invitations](invitations.md). Names are prefixed with `shared_` because `groups` is a keyword of SQLite.

- `profile` (migration `0010`): `user_id` (the key, references `user` and goes with it), `nickname` and `updated_at`. A row exists only while a nickname is set, and nothing is unique in it.
- `shared_groups` (migration `0011`): `id` (UUID made on the client), `kind` (`group` or `direct`), `name` (null for `direct`), `currency`, `simplify_debts` (0 or 1), `created_by`, `created_at`, `updated_at`, `deleted_at`. A group with `deleted_at` is closed.
- `shared_members`: `id` (UUID made on the client, what entries refer to), `group_id`, `user_id` (null for a placeholder), `name`, `role` (`owner` or `member`), `created_by`, `created_at`, `claimed_at`, `left_at`, `left_seq` (the cursor of the group when the member left, which is how far they read afterwards), `archived_at` (when that user archived a closed group), `merged_into` (the member a placeholder was merged into) and `show_in_expenses` (0 or 1, default 1: the switch of that user for that group). `claimed_at` is set for every member who is or was a user (the maker and a friend added are claimed when they are added), so a placeholder is a member without it. A member with an empty `name` is a person who deleted their account. Indexes: `(group_id)`, `(user_id)` for the groups of a user, a unique `(group_id, user_id)` where `user_id` is not null, and a unique `(group_id)` where `role` is `owner`, so a group has one owner (handing it over demotes the owner first, in the same batch). A member with a user has `claimed_at` (a `CHECK`), and `kind` and `role` are checked to be one of theirs.
- `shared_entries`: `id` (UUID made on the client), `group_id`, `kind` (`expense` or `settlement`), `text`, `category_id` (null for a settlement), `amount_cents` (greater than 0), `currency`, `date`, `paid_by` (a member id), `split` (`equal`, `percent` or `exact`), `shares` (JSON, `[{ "memberId", "cents" }]`), `payment` (`direct`, `credit` or `voucher`, default `direct`) and `charge_date` (how the payer paid, as in `expenses`), `created_by` and `updated_by` (user ids, set by the server, null once that user deleted their account, and answered as the members of those users in the group), `created_at`, `updated_at`, `deleted_at` and `seq`. `seq` is a counter per group, taken as `MAX(seq) + 1` for the group inside the upsert; unique `(group_id, seq)`. The group's cursor is that `MAX(seq)`, so the group has no counter of its own, and `left_seq` takes it in the same update that sets `left_at`. Money is cents as everywhere; the shares are the stored truth and no percentage is stored.
- `friend_invitations` (migration `0012`): `id` (a UUID made by the server, the key; the link carries it with a signature that is never stored in the table, [invitations](invitations.md)), `group_id` (a `direct` group, the friend), `member_id` (its placeholder), `created_by`, `created_at`, `expires_at` (after `created_at`, a `CHECK`), `accepted_by`, `accepted_at`, `declined_at` and `revoked_at`. At most one of the last three times is set (a `CHECK`), and `accepted_by` only with `accepted_at`; who declined or revoked is not kept. Indexes: `(group_id)`, a unique `(group_id)` where none of the three is set, so a friend has one open invitation, and one on `created_by` and on `accepted_by`.
- Access is always through the caller's member row: a user writes to a group only while they have a member row there with `left_at` null and the group is open, which the write of an entry checks in its own statement. They read it while they have a row there at all, up to `left_seq` if they left, which is what makes a closed group readable. `created_by` of a group, and the user columns of the invitations, are null once that user deleted their account; the user columns of the shared tables reference `user` with `ON DELETE SET NULL`, and each `created_by` and `updated_by` has an index, so deleting a user finds their rows without reading every row. A user's own rows (`expenses`, `categories`, `income`, `budget`) are untouched.
