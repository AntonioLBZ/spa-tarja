# Offline strategy

- **Shell**: PWA with `vite-plugin-pwa` (Workbox, `generateSW`) precaching the app. Navigations fall back to `index.html` except `/api/*`. Updates use `registerType: 'prompt'`: the new version waits until the user accepts it, so it never reloads the app halfway through an expense. Icons are generated from `public/favicon.svg` with `pnpm pwa:icons`.
- **Reads**: TanStack Query with the cache persisted in IndexedDB (`@tanstack/react-query-persist-client`, no expiry, only the `expenses`, `categories`, `income` and `budgets` queries), under the signed-in user's id ([authentication](authentication.md)). The cache holds everything the server has told this device, tombstones included, plus the cursor of the last change seen.
- **Writes**: a save never waits for the network. The expense, with its client UUID, goes into the **outbox**: an IndexedDB record of the latest version of each unsynced expense, so editing or deleting a pending expense replaces its entry. The screen shows the cached server data with the outbox on top, and marks the pending rows.
- **Sync** is the `queryFn` of the `expenses` query, so every trigger Query already has (app open, focus, reconnect, invalidation after a save) runs the same path: push the outbox in order, then pull what changed after the cursor. Safari has no Background Sync, so nothing depends on it. While entries are pending the query also retries every 30 s, for connections that report online but aren't.
- **Outbox rules**: an entry leaves the outbox only when the server answered it, and only if it wasn't edited meanwhile (same `updatedAt`). A network error or a 5xx stops the push and keeps the order for the next run. A 400 or 409 is permanent: the entry is dropped and the user is told.
- **Server**: idempotent `PUT /expenses/:id` (creates or updates by id), so retrying is safe. A delete is the same `PUT` with `deletedAt` set; there is no `DELETE` route. `GET /expenses?after=<seq>` pages through the changes after a cursor, tombstones included, and returns the new cursor.
- **Exceptions to the outbox**: the custom categories ([categories](categories.md)), the monthly income ([when an expense counts](expense-counting.md)) and the budgets ([budgets](budgets.md)) need a connection to be changed, and all of them are read from the persisted cache.
- **Conflicts**: last edit wins by `updatedAt`, enough for one user on several devices. The server applies a write only when its `updatedAt` is strictly newer than the stored one (so a retry changes nothing) and otherwise answers with the row it kept. Deletes are soft so the sync can propagate them. The clock is the device's: a device whose clock is behind loses to rows written ahead of it, silently.
- **Shared entries** ([ADR-0013](../adr/0013-shared-entries-sync-through-an-outbox.md)) follow the same rules with the group as the scope. The entries of a group go through a second outbox, the same code over its own key (`tarja:group-outbox:<user id>`), so the stored format of the first doesn't change. The sync of a group is the `queryFn` of its `group-entries` query: push that outbox in order, then pull what changed after the group's cursor (`GET /groups/:groupId/entries?after=`), so the same triggers run it. A device runs it for every group in `GET /groups`, one request each, which the `groups` query itself refreshes on open, focus and reconnect. The outbox treats `400`, `403`, `404`, `409` and `422` as permanent: the entry is dropped and the person told, as for an expense. The persisted cache gains the `groups` and `group-entries` queries, under the same user.
- **Needs a connection** (an addition to the exceptions above): making, renaming and deleting a group, adding, renaming, removing and leaving members, handing a group over, invitations, merging a dummy, the nickname, the switches Show in my expenses and Archive, the simplified debts switch and deleting the account. The lists and the entries of the groups already on the device are read from the local copy. A group that was deleted, or that the person left, comes back from `GET /groups` as closed and the device goes on reading it, read-only; a write to it is dropped as permanent (`409 closed`). The entries a device wrote offline to a group that closed meanwhile are refused the same way and the person is told ([groups](groups.md)).
- **Conflicts on shared entries** are last write wins by `updatedAt`, like the expenses. Two people editing one entry before they sync end with the later one; the server records who wrote last (`updatedBy`).
