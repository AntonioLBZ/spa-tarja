# Offline strategy

- **Shell**: PWA with `vite-plugin-pwa` (Workbox, `generateSW`) precaching the app. Navigations fall back to `index.html` except `/api/*`. Updates use `registerType: 'prompt'`: the new version waits until the user accepts it, so it never reloads the app halfway through an expense. Icons are generated from `public/favicon.svg` with `pnpm pwa:icons`.
- **Reads**: TanStack Query with the cache persisted in IndexedDB (`@tanstack/react-query-persist-client`, no expiry, only the `expenses`, `categories`, `income`, `budgets`, `groups` and `group-entries` queries), under the signed-in user's id ([authentication](authentication.md)). The cache holds everything the server has told this device, tombstones included, plus the cursor of the last change seen.
- **Writes**: a save never waits for the network. The expense, with its client UUID, goes into the **outbox**: an IndexedDB record of the latest version of each unsynced expense, so editing or deleting a pending expense replaces its entry. The screen shows the cached server data with the outbox on top, and marks the pending rows.
- **Sync** is the `queryFn` of the `expenses` query, so every trigger Query already has (app open, focus, reconnect, invalidation after a save) runs the same path: push the outbox in order, then pull what changed after the cursor. Safari has no Background Sync, so nothing depends on it. While entries are pending the query also retries every 30 s, for connections that report online but aren't.
- **Outbox rules**: an entry leaves the outbox only when the server answered it, and only if it wasn't edited meanwhile (same `updatedAt`). A network error, a 5xx or a 401 stops the push and keeps the order for the next run. A 400, 409 or 422 is permanent: the entry is dropped and the user is told. The outbox keeps what it dropped, with the `error` code of the answer, until the person dismisses the notice.
- **Server**: idempotent `PUT /expenses/:id` (creates or updates by id), so retrying is safe. A delete is the same `PUT` with `deletedAt` set; there is no `DELETE` route. `GET /expenses?after=<seq>` pages through the changes after a cursor, tombstones included, and returns the new cursor.
- **Exceptions to the outbox**: the custom categories ([categories](categories.md)), the monthly income ([when an expense counts](expense-counting.md)) and the budgets ([budgets](budgets.md)) need a connection to be changed, and all of them are read from the persisted cache.
- **Conflicts**: last edit wins by `updatedAt`, enough for one user on several devices. The server applies a write only when its `updatedAt` is strictly newer than the stored one (so a retry changes nothing) and otherwise answers with the row it kept. Deletes are soft so the sync can propagate them. The clock is the device's: a device whose clock is behind loses to rows written ahead of it, silently.
- **Shared entries** ([ADR-0013](../adr/0013-shared-entries-sync-through-an-outbox.md)) follow the same rules with the group as the scope. The entries of a group go through a second outbox, the same code over its own key (`tarja:group-outbox:<user id>`), so the stored format of the first doesn't change. The sync of a group is the `queryFn` of its `group-entries` query: push that outbox in order, then pull what changed after the group's cursor (`GET /groups/:groupId/entries?after=`), so the same triggers run it. A device runs it for every group in `GET /groups`, one request each, which the `groups` query itself refreshes on open, focus and reconnect. The screens that need it mount it: the Groups tab for every group, the screen of a group for that group, and the screens that add up the person's own expenses (home, the summary with the bars of the budgets, the charts), with the add form wherever it is (its budget warning counts them), for the groups whose Show in my expenses is on and for any group with a write of the person waiting. So a shared expense added at home is sent from there, with the triggers of the expenses (open, focus, reconnect, a save, and every 30 s while it waits), and a group whose switch is off is asked for there only while it has a write waiting. The outbox treats `400`, `403`, `404`, `409` and `422` as permanent: the entry is dropped and the person told, as for an expense, with the code of the answer, so a screen can say why. What the device shows goes back to the version the server kept (the answer carries no entry, so the pull that follows brings it when it changed). The refusals live in memory, as those of the expenses, so a reload forgets them: each is a `Notice` with its own Dismiss that names the entry, the group and the reason ([shared expenses](shared-expenses.md)). The persisted cache gains the `groups` and `group-entries` queries, under the same user.
- **Needs a connection** (an addition to the exceptions above): making, renaming and deleting a group, adding, renaming, removing and leaving members, handing a group over, invitations (making, revoking and listing the link of a friend, and reading, accepting and declining a link, which the device refuses offline before sending anything), merging a dummy, the nickname, the switches Show in my expenses and Archive, the simplified debts switch and deleting the account. The changes of a group and of its people (making, renaming and deleting it, adding, renaming, removing and merging people, handing it over, leaving, and the switches) are refused on the device before anything is sent while it knows it is offline, and all of them but the two switches of the person on a group closed for them. The lists and the entries of the groups already on the device are read from the local copy. A group that was deleted, or that the person left, comes back from `GET /groups` as closed and the device goes on reading it, read-only; a write to it is dropped as permanent (`409 closed`), and the group turns closed on the device at once, read as deleted until `GET /groups`, asked again then, says whether it was deleted or left. The entries a device wrote offline to a group that closed meanwhile are refused the same way and the person is told ([groups](groups.md)).
- **Leaving.** A person who left reads a group only up to `left_seq` ([groups](groups.md)), by `seq`, and the server keeps no older version of an entry: an entry edited or deleted after they left moves past that cursor, so they keep the version their device holds and never see the change, and an entry their device hadn't pulled before they left never reaches them, on that device or a new one. So leaving needs a connection, and the device first pushes the outbox of that group and pulls its changes, and asks to leave only when both went through and nothing of that group is left waiting (a write made meanwhile); otherwise the leave stops and says why. Being removed, or leaving from another device, can still leave a device short of the last changes, which is accepted.
- **Conflicts on shared entries** are last write wins by `updatedAt`, like the expenses. Two people editing one entry before they sync end with the later one; the server records who wrote last (`updatedBy`). Since a later `updatedAt` wins, one written from a clock set ahead would win over every edit of everybody until then, so the server refuses an `updatedAt` more than a day ahead of its own clock with `422 clock-ahead`: the outbox treats it as permanent like any `422`, and the app tells the person to check their clock.
- **A known limit of shared entries:** a tombstone keeps the whole entry (its text, amounts and shares), so a member who joins a group later reads its deleted expenses too, from cursor 0.
