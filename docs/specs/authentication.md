# Authentication

Google OAuth, no own passwords, through Better Auth mounted on Hono at `/api/auth/*`. Better Auth takes the D1 binding directly. It needs the `nodejs_als` compatibility flag (it uses `AsyncLocalStorage`).

- **Tables**: `user`, `session`, `account` and `verification`, in migration `0003`. They are written by hand, like the rest of the schema, and a test fails if Better Auth asks for a table or column the migration lacks.
- **What Google leaves.** The `user` row (name and email) is written at the first sign-in and never refreshed. The address of the picture Google sends is not kept: the app never shows it, so the Google provider maps the profile without it (`mapProfileToUser`, `server/auth.ts`) and `user.image` stays null, at the first sign-in and at every other. The `account` row keeps the Google account id (`accountId`), the provider and the scope, and none of the tokens Google sends: the app never calls Google after the sign-in, so a database hook (`databaseHooks.account`, `server/auth.ts`) sets `accessToken`, `refreshToken` and `idToken` to null whenever Better Auth creates or updates the row, which it does at every sign-in. The columns stay, since Better Auth's schema asks for them. Migration `0013` empties the tokens and the picture address of the rows written before, so none is left once it has run; a test applies it to rows that hold them. The IP address and the browser of a session are kept: they are part of the session and Better Auth's rate limiter reads the address.
- **Sessions**: `httpOnly` cookies signed with `BETTER_AUTH_SECRET` (the session token, the 5 minute cache of the session and, while a sign-in is on its way, its state), the session valid for 30 days. The `session` row keeps the IP address and the browser it was opened from. Signing out deletes the row; an expired one is deleted only if it is presented again, so a session that is simply no longer used stays until the account is deleted. The cache lets most requests skip reading the session from D1. A revoked session can therefore stay valid for up to 5 minutes, but a deleted account can't: every route that needs a session also reads the `user` row by its key (`withUser`, `server/user.ts`) and answers `401` when it is gone. The cookie has no `Domain` (cross-subdomain cookies stay off), so it belongs to `tarja.albz.app` alone and the other sites under `albz.app` never see it. Every window sends the id of the user it was opened for in `X-Tarja-User` on each call to `/api` but `/api/auth/*` and `/api/health`, since the browser's cookie is shared by all its windows and can change to another account under one left open; `withUser` answers `401 { error: 'other-user' }` when the header is there and is not the session's user (a request with no header, like curl, is served), so a window never reads or writes with another account's session. The `401` makes the app ask `get-session` again, which mounts the real user; the app also asks when a window becomes visible and when another window stores or forgets the session (`tarja:session`), and the outboxes of the window that is left stop sending.
- **Base URL**: the origin of each request, so the same code runs on `localhost`, `tarja.albz.app` and any other origin without configuration. Cloudflare only routes the Worker's own hosts, Google only redirects to the URIs registered in its console, and Better Auth rejects cross-origin `POST`s against that origin.
- **Framing**: the app is never shown inside another page, since the session cookie is `SameSite=Lax` and a page on a sibling site under `albz.app` could otherwise frame the signed-in app and get clicks on its buttons. Every response carries `Content-Security-Policy: frame-ancestors 'none'`, `X-Frame-Options: DENY` and `Referrer-Policy: strict-origin`. The Worker sets them on all its `/api` answers, errors and the redirects of Better Auth included, with one middleware (`withFramingHeaders`, `server/headers.ts`) that copies the answer first, so an answer whose headers can't be changed takes them and the cookies it sets stay as they are; the HTML and the other static files, which the Worker never serves, get them from `public/_headers` (`/*`), which the build copies to the assets folder, where Cloudflare reads it and does not serve it as a file. The tests cover the Worker; the static file is not exercised by them. The `<meta name="referrer">` stays for the case where the headers are not there.
- **Writes from another origin**: the session cookie is `SameSite=Lax`, which a sibling site under `albz.app` shares, and one write takes no body and no custom header (`POST /api/invitations`), so a page there could make it with the person's cookie and no preflight. A small middleware (`withOwnOrigin`, `server/origin.ts`) runs on every `POST`, `PUT`, `PATCH` and `DELETE` of `/api` but `/api/auth/*`, whose writes Better Auth checks itself: when the request has an `Origin` header that is not the request's own origin (`new URL(origin).origin` against `new URL(request.url).origin`; the literal `null` and anything that is not a URL included) it answers `403 { error: 'bad-origin' }` before the session is read, with the framing headers on it, and nothing is written. A request with no `Origin`, which is not from a browser, goes through, and so does a read, from anywhere. The dev server and the tests send the origin of the request or none, so they pass.
- **Access**: `/api/expenses`, `/api/categories`, `/api/income`, `/api/budgets`, `/api/profile`, `/api/groups` and `/api/invitations` answer `401` without a session; `/api/health` and `/api/auth/*` are public. The owner of every row is the Better Auth `user.id`. Any Google account can sign in. Rows saved while the login didn't exist belong to the old fixed user and are unreachable now.
- **Privacy.** The sign-in screen has a ghost `Button` under the Google button that opens the privacy notice, a `Dialog` ([settings](settings.md)), so it can be read before signing in. Its text is in the bundle: it opens with nobody signed in, with the server out of reach and offline, and sends no request, and pressing it starts no sign-in.
- **Back to the invitation.** `startSignIn` sends the current path as the `callbackURL` when it is exactly the link of an invitation, `/join/` and a token of the token's shape with nothing after it (`invitationPath`), and `/` otherwise, so signing in from an invitation link lands on the link ([invitations](invitations.md)). Only a path of the app of that shape is ever sent, so the way back can't be pointed anywhere else. That path carries the signature of the link, and Better Auth keeps the `callbackURL` of a sign-in in its `verification` table for at most 10 minutes (longer if the sign-in is abandoned, until its record is cleaned up). That is the one place outside the invitation tables where a signed link is held. On such a link the sign-in screen says that signing in shows the invitation. The error callback is the same path with `?signin=failed`, and `/?signin=failed` when it is not an invitation link, so a sign-in that fails on a link comes back to the link, with the failed notice and the invitation line, and the person still has it in the address bar. The error callback is kept in that same record, so the link is held no longer and in no other place.
- **Client**: no Better Auth client, to keep the bundle small. Three calls (`src/lib/auth/service.ts`): `GET /api/auth/get-session?disableCookieCache=true` (past the cookie cache, so that a device asks D1 itself and learns at once that the account was deleted from another one; it asks only on open, on reconnect after an open that couldn't ask, after a `401`, when the window becomes visible and when another window stores or forgets the session), `POST /api/auth/sign-in/social` (the answer carries the Google URL to go to; Google sends the person back to the path the sign-in started from if it is an invitation link, else to `/`, or to the same path with `?signin=failed` when it did not go through) and `POST /api/auth/sign-out`. A small store (`createAuth`) holds the state: `loading`, `signed-out` (with `unreachable` when the server couldn't be asked) or `signed-in`. `AuthGate` shows the sign-in screen to everybody but a signed-in user, and `AppProviders` (`src/providers.tsx`) mounts the whole app inside it.
- **Offline**: the signed-in user's profile is kept in `localStorage`, so the app opens signed in with no network. Only a definite answer signs the user out: a `get-session` with no session, or a `401` from the API. A network error or a `5xx` never does. The local copy goes with the session, as below. Without a cached profile and without a connection there is nothing to show but the sign-in screen, which says so.
- **Local data belongs to a user**: the two outboxes and the persisted cache are stored under the user id (`tarja:outbox:<id>`, `tarja:group-outbox:<id>`, `tarja:query-cache:<id>`; `createUserStorage`), and so is the group last shared with (`tarja:shared-with:<id>`, in `localStorage`, forgotten by the same `discard`), so another account on the same browser never sees or pushes them. `UserDataProvider` builds them for the signed-in user and is remounted when the user changes. A `401` from any query or mutation makes the app ask `get-session` again (`createQueryClient({ onUnauthorized })`); an unsynced expense is kept, as a `401` is not a permanent refusal. The user's local data (the group last shared with included) is deleted whenever the user is signed out, whether by the Sign out button or by the server saying so (the session expired, or the account was deleted from another device), and only when nothing is waiting to sync in either outbox, in this window or on the device (another window may have saved a write since this one opened, so both outbox keys are read from storage too); otherwise it stays for the next sign-in of that user. That rule is in one place, `UserDataProvider`, which runs it when the tree it belongs to is unmounted because the state turned `signed-out`; a network error never signs anybody out, so it never deletes anything, and another account taking over the browser deletes nothing either. Signing out needs a connection, because the cookie is `httpOnly` and only the server can end it. Data stored before the login existed sits under the old unscoped keys and is never read.
- **Secrets**: `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, in `.dev.vars` locally (`.dev.vars.example` lists them) and in `wrangler secret` in production. Google's console must list `<origin>/api/auth/callback/google` for each origin in use; in production that is `https://tarja.albz.app/api/auth/callback/google`.
- **Deleting the account** ([ADR-0014](../adr/0014-people-in-groups.md)). `DELETE /api/account` with `{ email }` (the account's own, typed to confirm, in any case and with spaces around it, by the check the dialog uses, `confirmsEmail` in `core/account.ts`; any other is `422 wrong-email` and deletes nothing) needs a connection and a session, and does everything in one D1 batch, all or nothing. It answers `204` with no body, and expires the cookies of the session through Better Auth's own sign-out; if that last step fails the answer is still `204`, since the data is gone and a cookie left behind belongs to a session that answers `401`. No balance holds it back: the balances stay in the ledgers, below.
    - It deletes the user's `expenses`, `categories`, `income`, `budget` and `profile`, and revokes the open invitations they made, so their links answer as gone. An invitation they accepted stays accepted, by nobody, and the friend it made goes on as below.
    - **Groups nobody else can read are erased.** A group they are in, open, closed or left, where no other member has an account (a member who left keeps theirs and counts, one who deleted theirs has none: `user_id` is null) holds only placeholders, or only people who deleted their accounts, and nobody could read it once the account is gone. The batch deletes it first, in foreign key order: its invitations (by group), then its entries, its members (`merged_into` cleared before) and the group itself, so no group name, no name of a placeholder and no text of an entry is left. A group where somebody else has an account, a leaver included, is not erased and goes on as below. A friend is one of them while the other side has an account.
    - In the other groups, open or closed, their member keeps its row but loses the user and the name (`user_id` null, `name` empty), so the screens show "Deleted user", and so does every placeholder merged into it (`merged_into`), since the name a group typed for a person before they joined is most often their own: it loses its name too, and goes on being read as that member. The entries are left as they are: they are also the record of the others, and the balances don't move. `created_by`, `updated_by` and the other user columns of the shared tables are set to null. The rest of the group can settle that member's balance with a settlement, or remove them once it is zero, like a placeholder.
    - A group they owned goes to the member who is a user, hasn't left and joined first (by `claimed_at`), open or closed. When there is none, the group is deleted and closed, and it has no owner from then on, since nobody is left to act for it. A group where everybody else has left is closed the same way.
    - **A friend ends for the other person.** An open friend whose other side has an account is closed for that person in the same batch, exactly as when a friend is deleted (`deleted_at` and `updated_at` set): it leaves their Friends and their friends to pick from, shows under their closed groups as no longer a friend, and keeps its entries, read-only, with the balance it had (no balance holds the deletion back, and the one left can settle nothing, as a closed group offers no settle up). It is owned by the person left. Its other member is the one who deleted the account, with no name. The person left can archive it like any closed group, and the cap of closed groups never stops the deletion, since it is checked only by the writes that put somebody in a group. A friend already closed stays as it was, and one whose other side deleted their account before, closed then, is erased now (above). An open friend therefore always has a real person on the other side, and adding to a group a friend whose other side is gone is refused as any closed friend is (`422 unknown-friend`).
    - In the batch, the groups nobody else used are erased first, then the open invitations are revoked, then those groups and the friends close, the user steps down as owner before anybody takes over (a group has one owner), their members and the placeholders merged into them lose the name, their own data goes, and the `user` row goes last, since their members are found by their `user_id` until then.
    - Then it deletes the `user` row, and the sessions and accounts (with the Google account id) go with it through their cascades, so every session of the user, on every device, answers `401` at once, also one held by its cookie cache (above). Nothing in `verification` belongs to a user: it holds the state of sign-ins on their way, which expires by itself. The browser forgets the cookie, the device deletes its local data under the user id (both outboxes, the cache and the group last shared with) and signs out on its own (`forget`), and the sign-in screen shows, saying that the account was deleted, or, when the device couldn't delete its copy, that it couldn't and that clearing the site's data in the browser removes it. Another device of the user learns it from its next `401`. There is no state of an invitation on the device to delete: a link lives only in the address, and the list of the person's own links only in memory.
    - **Nothing is sent meanwhile.** From the moment the request leaves, both outboxes of the device are paused (`pause` on the `Outbox`): the push loops send nothing for that user, and what waits stays on the device until the account is gone and its copy is deleted, or, if the deletion fails, until they resume. A write already in flight when the batch runs can still land: an `expenses` row has no foreign key to `user`, so a `PUT /api/expenses/:id` that passed `withUser` just before the batch can insert a personal row for a user who no longer exists, which nothing deletes. It is unreachable (no session can ask for it), and it holds nothing shared: the shared tables name their writers by a foreign key to `user`, so a shared write that comes after the `user` row is gone is refused.
    - It is irreversible. The screen offers the export first ([settings](settings.md)), and says that the backups D1 keeps for recovery expire on their own. The privacy notice, which says all this, is in the settings and on the sign-in screen ([settings](settings.md)).
