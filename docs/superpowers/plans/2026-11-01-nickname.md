# Nickname Implementation Plan

**Goal:** A signed-in person can set, change and remove the nickname their friends see, from Settings → Profile, while online.

**Architecture:** One schema in `core/profile.ts` shared by the client and the Worker. Migration `0010` adds `profile` (a row only while a nickname is set). `GET` and `PUT /api/profile` behind `withUser` answer `{ nickname, name }`, never the email. The client reads it with `profileQuery` (not persisted: it needs a connection, like the categories) and writes it with `putProfile`, putting the answer in the cache.

**Spec:** `docs/specs/invitations.md` (Nickname, Screen), `docs/specs/settings.md` (Profile), `docs/specs/data-model.md` (`profile`), `docs/specs/authentication.md` (Access), `docs/adr/0014-people-in-groups.md`.

## Choices where the docs are open

- The nickname is 1 to 30 characters after trimming (the spec; the milestone brief said 40, the spec wins).
- `PUT` takes `{ nickname: string | null }`: `null` removes it; a string that is blank after trimming is a `400`, as the spec's "1 to 30" says. The screen sends `null` when the field is empty, so saving an empty field removes the nickname too (the spec gains that line).
- `profile.user_id` references `user` with `ON DELETE CASCADE`, like `session` and `account`.
- The hint ends with the account name (`{name}`), which is what `GET` returns it for; before the profile has loaded it is the name of the session.
- The section sits after the app color, which belongs with the theme, and before Categories (`settings.md` lists it there).
- The field is not turned off while the profile loads: what was typed is a draft over the stored value, so a late answer never overwrites it.

## Review Focus

- The email must never reach `/api/profile`: the read selects only `nickname` and `name` (tested on the body).
- `PUT` for a user whose row is gone (a deleted account whose cookie cache is still valid) fails the foreign key and answers `500`; not tested, and item 29 owns that path.
- A `401` from `putProfile` doesn't ask the session again (the actions call the API directly, like the categories and the income); only the query's `401` does.
- Offline after a reload the profile isn't in the persisted cache, so the field is empty and off with the notice; not a regression, but it reads as "no nickname" until back online.
- The bottom bar hides while the field has the focus (existing behavior), checked by hand only.
